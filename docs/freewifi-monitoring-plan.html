Device-level tracking— nothing exists —BUILD · the core gap

The gap in one sentence: the app can tell you a site was down yesterday because someone typed it in — it cannot tell you which router, with which serial, stopped heartbeating at 02:14, or that its battery voltage has been sliding for three nights.

PHASE 1 · FOUNDATIONDevice registry

New domain: device catalog → devices → deployments. Spec sheets live on the model, physical reality lives on the unit, assignment history lives between unit and site.

device_models — catalog of spec sheets
├─ id, manufacturer, model_name, model_number
├─ type            enum: outdoor_ap, router, switch, cpe, solar_panel,
│                        charge_controller, battery, ups, poe_injector,
│                        antenna, camera, other
├─ wifi_standard   enum: wifi4 … wifi7, none
├─ specs           JSON: { radio_bands, max_throughput_mbps, max_clients,
│                          poe_standard, power_draw_w, ip_rating,
│                          temp_range_c, antenna_gain_dbi, ports,
│                          sim_slots, capacity_ah, wattage }
└─ datasheet_url, photo_path, is_active

devices — each physical unit
├─ id, device_model_id FK
├─ asset_tag       unique — printed QR label
├─ serial_number   unique
├─ mac_address     nullable, unique
├─ firmware_version, notes
├─ status          enum: in_stock, deployed, under_repair, retired, lost
├─ condition       enum: new, good, degraded, faulty
├─ purchase_order_no, supplier, unit_cost, purchased_at, warranty_until
└─ timestamps, soft_deletes

device_deployments — assignment history over time
├─ id, device_id FK, site_id FK
├─ role_at_site    enum: primary_ap, backup_ap, backhaul, power, surveillance, other
└─ installed_at, removed_at, installed_by, install_notes

maintenance_logs
├─ id, device_id nullable FK, site_id nullable FK
├─ type            enum: inspection, repair, firmware_upgrade, replacement,
│                        cleaning, reboot
└─ performed_by, performed_at, downtime_minutes, cost, findings, actions_taken, photos JSON

Phase 1 features

  • Device CRUD with catalog-driven forms — specs auto-fill from the chosen model, overridable per unit.
  • QR asset tags — printable labels encoding asset_tag; scanning opens the device page so a field tech gets full history on their phone.
  • "Equipment" tab on each site — everything installed there, with roles and install dates.
  • Inventory views — stock counts per type, deployed-vs-spares ratio, warranty-expiry report.
  • Devices.xlsx import template — reuses the existing FreewifiImportBatch queue machinery.

PHASE 2 · LIVE HEALTHMonitoring & alerting

Turn manual UP/DOWN entries into automated telemetry — while keeping human approval as the override for reporting integrity.

Ingestion path 1 — heartbeat API (ship first)

POST /api/v1/heartbeat, authenticated by a Sanctum token minted per site/device. The router or CPE controller POSTs every five minutes; a missing heartbeat is the offline event.

POST /api/v1/heartbeat
{
  "site_code": "AP-XXX",
  "device_serial": "...",
  "uptime_s": 86400,
  "firmware": "v2.1",
  "cpu_pct": 12, "mem_pct": 41,
  "wan_latency_ms": 23,
  "clients_connected": 14,
  "bw_rx_mbps": 18.4, "bw_tx_mbps": 6.2,
  "power": { "source": "solar", "battery_v": 13.1, "solar_w": 45 }
}

Ingestion path 2 — controller polling (when reachable)

A scheduled Laravel command SNMP-GETs each site gateway (sysUpTime, ifHCInOctets, ifHCOutOctets, hrProcessorLoad) every five minutes and writes the same metric rows. Both paths converge on identical storage, so dashboards don't care where the numbers came from.

device_metrics      raw time-series — indexed (device_id, ts); pruned to hourly
                    rollups after 90 days
site_status_events  transitions UP→DOWN→UP — started_at, resolved_at,
                    cause: heartbeat_lost | poll_failed | manual | planned_maintenance
alert_rules         metric + operator + threshold + duration + severity + notify_roles
alerts              fired instances — triggered_at, acknowledged_at/by,
                    resolved_at, escalation_level

  • Notifications: email first; SMS through your existing jelite SMS API for critical alerts routed to field techs by territory; optional Telegram/Discord webhook for the NOC channel.
  • NOC wallboard dashboard: live Online / Down / Degraded / No-data counters, the Philippine map recolored by real-time state, active-alert feed, longest-currently-down list. Inertia partial reloads every 60 s.
  • Time-series charts per site and device — uptime, users, throughput, latency, battery voltage (Chart.js or uPlot).
  • Nightly auto-fill of site_daily_statuses from metrics; APPROVED/LOCKED stays as the human override.

PHASE 3 · OPERATIONSTickets, SLA & field tools

  • Lightweight maintenance tickets built in — issue → assign tech → resolve with photos and downtime minutes; feeds MTTR stats. Deep integration with pred-ticket-rag can come later.
  • SLA reports — monthly availability per site/district/province vs target (≥97%), users served, data delivered, incident count, MTTR; extends the DomPDF pipeline.
  • Firmware fleet view — which units run which versions, rollout progress.
  • Power analytics for solar sites — overnight battery curves, days-to-failure projection.
  • Field inspection form — mobile page: scan QR → checklist → photo upload → GPS confirm.
  • Public transparency mini-portal (optional) — unauthenticated live map of active sites and headline stats.
